Last Updated: 2026-01-16
Purpose: Comprehensive QA guide for testing Salesforce ↔ Dynamics 365 integration via MuleSoft
Audience: QA Engineers, Test Automation Engineers

📋 Overview

What We're Testing

End-to-end integration between Salesforce and Dynamics 365 via MuleSoft, where:

  • Salesforce is the source of truth for Account, Contact, AccountTeamMember, and Country records
  • MuleSoft is the integration layer (treated as black box)
  • Dynamics 365 is the target system where data is synchronized

Integration Flow

Salesforce Record
→

→
MuleSoft
→
Dynamics
→
Dataverse_ID__c Updated

Key Principles

1. Black Box Testing: We don't test MuleSoft directly - we verify end-to-end behavior

2. Event-Driven: Integration is triggered by Platform Events

3. Asynchronous: Processing happens asynchronously (wait 3-10 seconds)

4. Correlation: Use Party MasterId for linking records across systems

🧪 Testing Approach

Test Strategy

  1. Create Test Data in Salesforce
    • Use existing step definitions from src/step-definitions/common/data-factory.steps.ts
    • Create Account, Contact, AccountTeamMember records
  2. Trigger Integration
    • Update Account Status to "Active" or "Onboarding"
    • Create Contact (requires parent Account with Dataverse_ID__c)
    • Add AccountTeamMember (requires parent Account with Dataverse_ID__c)
  3. Wait for Processing
    • Wait 3 seconds for MuleSoft processing
    • Use polling strategy (check every 3 seconds, max 10 seconds)
  4. Verify in Dynamics
    • Query Dynamics using Party MasterId (accelins_partyid)
    • Verify field mappings
    • Verify Dataverse_ID__c is populated in Salesforce

🎯 Common Test Scenarios

Scenario 1: Account Create & Sync

  1. Create Account with Status "Prospect"
  2. Verify Dataverse_ID__c is null
  3. Update Status to "Active"
  4. Wait 3 seconds
  5. Verify Dataverse_ID__c is populated
  6. Query Dynamics using Party MasterId
  7. Verify Party exists and fields match

Scenario 2: Contact Create & Sync

  1. Create Account with Status "Active"
  2. Wait for Account sync (verify Dataverse_ID__c populated)
  3. Create Contact linked to Account
  4. Wait 3 seconds
  5. Verify Contact Dataverse_ID__c is populated
  6. Query Dynamics Contact using Party MasterId
  7. Verify Contact exists and parent Party lookup matches

Test File: src/features/integration/mulesoft/contact-external.feature

Scenario 3: AccountTeamMember Create & Sync

  1. Create Account with Status "Active"
  2. Wait for Account sync
  3. Add AccountTeamMember
  4. Wait 3 seconds
  5. Query Dynamics Internal Contact
  6. Verify Internal Contact exists with status "Active"
  7. Delete AccountTeamMember
  8. Wait 3 seconds
  9. Verify Internal Contact status = "Inactive"

Test File: src/features/integration/mulesoft/contact-internal.feature

Scenario 4: Field Mapping Validation

  1. Create Account with specific field values
  2. Trigger integration
  3. Query Dynamics Party
  4. Verify field mappings match expected values
  5. Verify picklist value mappings (via Custom Metadata)

Test File: src/features/integration/mulesoft/account-billingcountry.feature

Scenario 5: Negative Scenarios

Invalid Data:
  • Account with invalid Country (no mapping)
  • Contact with invalid email format
  • Contact with missing FirstName
  • AccountTeamMember with User missing Azure AD Object ID
Expected Behavior:
  • Record not synced to Dynamics
  • Dataverse_ID__c remains null
  • Exception logged (to be verified)

🔧 Troubleshooting Guide

Issue: Dataverse_ID__c Not Populated

Possible Causes:
  1. Account Status not eligible (must be "Active" or "Onboarding" for Member)
  2. Missing field mappings (Country, State, etc.)
  3. MuleSoft processing error
  4. Insufficient wait time
Debugging Steps:
  1. Verify Account Status is eligible
  2. Check Custom Metadata for required mappings
  3. Increase wait time to 10 seconds
  4. Check MuleSoft logs (if accessible)
  5. Verify Platform Event was published

Issue: Contact Not Syncing

Possible Causes:
  1. Parent Account Dataverse_ID__c is null
  2. Invalid email format
  3. Missing FirstName or LastName
  4. Parent Account not synced yet
Debugging Steps:
  1. Verify parent Account has Dataverse_ID__c populated
  2. Check Contact email format
  3. Verify FirstName and LastName are present
  4. Ensure parent Account was synced first

Issue: Internal Contact Not Syncing

Possible Causes:
  1. Parent Account Dataverse_ID__c is null
  2. User missing Azure_AD_Object_ID__c
  3. AccountTeamMember not eligible
Debugging Steps:
  1. Verify parent Account has Dataverse_ID__c populated
  2. Check User has Azure_AD_Object_ID__c populated
  3. Verify AccountTeamMember was created successfully

Issue: Field Mappings Don't Match

Possible Causes:
  1. Custom Metadata mapping missing
  2. Incorrect field value in Salesforce
  3. Transformation logic issue
Debugging Steps:
  1. Query Custom Metadata to verify mapping exists
  2. Verify Salesforce field value
  3. Check Integration Design Document for transformation rules
  4. Verify Dynamics field value format

✅ Best Practices

1. Test Data Isolation

  • Use unique test data names (timestamp-based)
  • Clean up test data after execution
  • Avoid reusing test data across scenarios

2. Wait Strategy

  • Always wait 3 seconds after triggering integration
  • Use polling if needed (check every 3 seconds, max 10 seconds)
  • Don't assume immediate synchronization

3. Correlation Key Usage

  • Always use Party MasterId (Party_MasterId__c / accelins_partyid) for correlation
  • Don't use SalesforceID for Dynamics queries
  • Verify Dataverse_ID__c is populated before querying Dynamics

4. Field Mapping Validation

  • Use existing step definitions for field validation
  • Reference Custom Metadata for expected mappings
  • Test both positive and negative scenarios

5. Error Handling

  • Test negative scenarios (invalid data, missing mappings)
  • Verify exception handling (records not synced)
  • Document expected behavior for error cases

6. Code Reusability

  • Use common step definitions from src/step-definitions/common/
  • Reuse MuleSoft integration steps
  • Follow existing patterns in feature files

7. Test Organization

  • Group related scenarios in same feature file
  • Use descriptive scenario names
  • Add unique test case IDs (e.g., @INT-UI-001)
  • Tag scenarios appropriately

⚡ Quick Reference

Eligibility Rules

Entity Eligibility Criteria
Account Status = "Onboarding" (Type=Member) OR "Active" (other types)
Contact Parent Account has Dataverse_ID__c populated
AccountTeamMember Parent Account has Dataverse_ID__c AND User has Azure_AD_Object_ID__c

Wait Times

  • Initial Wait: 3 seconds
  • Polling Interval: 3 seconds
  • Maximum Wait: 10 seconds

Correlation Keys

  • Account/Party: Party_MasterId__c (SF) ↔ accelins_partyid (D365)
  • Contact: Parent Account Dataverse_ID__c → Party lookup
  • Internal Contact: User Azure_AD_Object_ID__c → systemuser lookup

Key Fields

  • Account: Party_MasterId__c, Dataverse_ID__c, Account_Status__c
  • Contact: Dataverse_ID__c, AccountId
  • AccountTeamMember: AccountId, UserId
  • User: Azure_AD_Object_ID__c
