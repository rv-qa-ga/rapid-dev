SECTION A — BUSINESS & FUNCTIONAL REQUIREMENTS

1. Overview

1.1 Purpose

This document defines the end-to-end functional design for synchronising data from Salesforce into Dataverse and Dataverse into Salesforce using MuleSoft as the integration layer.
It describes business rules, mappings, transformations, validations, and expected scenarios.

3. Business Transformation Rules

The Exception process still needs to be defined

Account Type → Dataverse Party Type

  • Salesforce will be the master for Party Types going forward, with the Account Type picklist defining the authoritative list of valid types. Dataverse will continue to maintain Party Types as reference records with unique IDs, as required for its lookup model.

  • The Party Types will be identified using a unique alternate key (e.g., PTP-000006).

  • Because Salesforce picklist labels and Dataverse party type identifiers are not the same thing, Salesforce will also store a mapping record that links:

  • Salesforce Account.Type → Dataverse Party Type Identifier (alternate key / master ID)

  • MuleSoft uses this relationship record to transform Salesforce Account records into Dataverse Party lookups.

Integration:

  1. Salesforce masters the party type list and this is represented in the Account Type picklist.

  2. Salesforce provides the party type name (Insurer, Member etc) and the relevant Account.Type → Dataverse Party Type ID mapping record.

  3. MuleSoft looks up the mapping for the Account.Type value.

  4. MuleSoft sets the Dataverse Party’s party type reference using the mapped Dataverse identifier.

  5. MuleSoft enters the party in Dataverse

  6. Dataverse resolves the Party type lookup internally using the alternate key.

  • If the Account.Type does not appear in the Salesforce mapping table following the defined exception process (this needs to be defined)

Status Rules for Account

Salesforce maintains a single business status field on the Account (Account_Status__c). Dataverse requires two related fields on the Party record to represent status:

  • statecode – high-level record state (Active / Inactive)

The Salesforce Account status must be translated into a paired Dataverse statecode and statuscode. This translation is performed by MuleSoft at runtime using mappings held in Salesforce.

Address Transformation Rules

Salesforce stores the address as a single combined field, with multiple parts separated by a comma. Dataverse has two address lines. When integrating from Salesforce to Dataverse:

  • The entire value of BillingStreet from Salesforce will be written directly into address line 1

  • No splitting of the string is performed, regardless of how many commas or segments are present.

  • Dataverse Address Line 2 will be left null in all cases

  • No attempt will be made to parse or populate additional lines

Trim whitespace

Leading and trailing spaces must be removed.
Example: " 123 Main Street " → "123 Main Street".

Respect Dataverse length limits

If BillingStreet exceeds the maximum length allowed for Dataverse Address Line 1,
→ the record must follow the exception process (needs to be defined)

Billing State and Billing Country Integration on Account

Salesforce stores State and Country values as picklist fields on the address object. Dataverse stores State and Country reference data tables, where the Party record looks up to:

  • accelins_country

  • accelins_state

Salesforce stores a mapping table between the BillingState and BillingCountry picklist values and the Master Ids for the accelins_country and accelins_state values in Dataverse. The Master Ids are used as an alternate key.

Salesforce → Dataverse

  1. Salesforce sends plain text strings (e.g., Country = ‘United Kingdom’) and stores the mapping for BillingState → accelins_state and BillingCountry → accelins_country.

  2. MuleSoft looks up the mapping for the BillingState and BillingCountry value

  3. MuleSoft sets the Dataverse fields accelins_country and accelins_state with the alternate key from the mapping table.

  4. MuleSoft sets the party record in Dataverse with the alternate keys for accelins_country and accelins_state.

  5. Dataverse resolves the fields using the alternate key provided.

A record must not sync to Dataverse if:

  • The Salesforce Country picklist value has no match in the mapping table

  • The Salesforce State picklist value has no match in the mapping table

The record must following the defined exception process (needs to be defined)

Functional Currency Mapping

Salesforce and Dataverse represent currency differently:

  • Salesforce uses its native multi-currency feature, storing ISO currency codes (e.g., GBP, EUR, USD).

  • Dataverse stores currency in a reference table and the parties table (accelins_party) stores a lookup to this Dataverse currency record for the functional currency.

  • Salesforce stores a mapping table between functional_currency_c in the account and accelins_functional_currency in the parties table. The Master Id is used as the alternate key.

Salesforce → MuleSoft → Dataverse

  • Salesforce sends the CurrencyISOCode value and stores the mapping between account.functional_currency_c and accelins_party.accelins_functional_currency_c.

  • MuleSoft looks up the mapping for the account.functional_currency_c value.

  • MuleSoft sets the accelins_functional_currency field using the mapped Dataverse identifier

  • Dataverse resolves the accelins_functional_currency lookup using the alternate key

If a mapping value is missing in the Salesforce mapping table the record must go through the exception process (to be defined)

Contact and Account Relationship Mapping

  • In Dataverse a contact record contains a lookup to the party it relates to.

  • In Salesforce a contact record contains a lookup to the Account record it relates to.

The integration must preserve this parent–child relationship when synchronising Contacts from Salesforce to Dataverse. Because Salesforce Accounts and Dataverse Parties use different identifiers, MuleSoft resolves the relationship using the Dataverse ID stored on the Salesforce Account.

  • MuleSoft receives the Salesforce Contact, including the Contact.AccountId.

  • MuleSoft performs a lookup/join to Salesforce Account using the Contact’s AccountId.

  • From the Account, MuleSoft retrieves the Dataverse Party ID, stored in Salesforce as:
    Account.Dataverse_ID__c

  • MuleSoft uses this value (Dataverse_ID__c) as the foreign key when creating or updating the Dataverse Contact:

  • MuleSoft sets the Dataverse Contact’s party lookup to the Dataverse Party ID obtained from the Account.

  • Salesforce IDs are therefore used only to locate the correct Salesforce Account, and the lookup to the Party in Dataverse is maintained using Dataverse-native identifiers.

Contact Name & Email Integration Rules

Email Address:

  • Must only send validly formatted email addresses.

  • If the email fails basic format checks (missing ‘@', missing domain, invalid characters, multiple '@’ signs etc) the record must:

    • Not be integrated into Dataverse

    • Be written to the exception list

    • Reprocess automatically when corrected in Salesforce

  • Email addresses must be lowercased before sending to Dataverse.

  • If the email field is empty or blank in Salesforce, Dataverse should receive null.

  • Email must not be used as a key to identify or match contacts.

  • If the email address length exceeds Dataverse max length, it must not sync and it must be logged as an exception.

First and Last Name:

  • First and Last name are mandatory, so if these are missing they must be blocked from integration and logged as exceptions.

  • Leading and trailing spaces must be trimmed

  • Multiple spaces collapsed into a single space

  • Allowed:

    • Letters

    • Hyphens

    • Apostrophes

    • Accented characters

    Not allowed:

    • Numerals

    • Emoji

    • Control characters

    • Any characters rejected by Dataverse text fields

    If disallowed characters are present, the Contact must go to the exception list.

  • If Salesforce values exceed Dataverse’s max length for first/last name:

    • The record must not sync

    • No automatic truncation is allowed

    • It must be logged as an exception

Internal Contact and Account Team Member Relationship Mapping

  • In Dataverse an internal contact record contains a lookup to the party it relates to.

  • In Salesforce a Account Team Member record contains a lookup to the Account record it relates to.

The integration must preserve this parent–child relationship when synchronising Account Team Members from Salesforce to Dataverse. Because Salesforce Account Team Members and Dataverse Internal Contacts use different identifiers, MuleSoft resolves the relationship using the Dataverse ID stored on the Salesforce Account.

  • MuleSoft receives the Salesforce Account Team Member, including the AccountTeamMember.AccountId.

  • MuleSoft performs a lookup/join to Salesforce Account using the Account Team Members AccountId.

  • From the Account, MuleSoft retrieves the Dataverse Party ID, stored in Salesforce as:
    Account.Dataverse_ID__c

  • MuleSoft uses this value (Dataverse_ID__c) as the foreign key when creating or updating the Dataverse Internal Contact:

  • MuleSoft sets the Dataverse Internal Contacts party lookup to the Dataverse Party ID obtained from the Account.

  • Salesforce IDs are therefore used only to locate the correct Salesforce Account, and the lookup to the Party in Dataverse is maintained using Dataverse-native identifiers.

Account Team Member - UserId Approach

  • Dataverse Internal contacts reference Dataverse Users via the Dataverse user GUID.

  • Because both Salesforce and Dataverse users originate from Azure Active Directory, the Azure AD Object ID is the only identifier that is consistent across both systems.

Salesforce

  • Each Salesforce User record stores the user’s Azure AD Object ID (e.g., in Azure_AD_Object_ID__c).

  • This ID is guaranteed to match the Azure AD Object ID stored on the corresponding Dataverse systemuser record.

Dataverse

  • The systemuser table stores the Azure AD Object ID for each user.

  • This field is defined as a unique alternate key in Dataverse.

Salesforce → Dataverse Flow

  1. MuleSoft receives the Account Team Member, including its UserId.

  2. MuleSoft retrieves the Azure AD Object ID from the Salesforce User record:

    • User.Azure_AD_Object_ID__c

  3. MuleSoft sends the Azure AD Object ID to Dataverse.

  4. Dataverse resolves the correct user using the alternate key:

    • systemuser.azureactivedirectoryobjectid = <Azure AD Object ID>

  5. MuleSoft creates or updates the internal contact record using:

    • The Dataverse user GUID (resolved by Dataverse)

Account Team Member → Internal Contact Status

Salesforce does not expose an explicit Status on Account Team Members; instead, the presence of an AccountTeamMember row indicates that a user is active on an Account.

  • Create / Add to Account Team

    • An AccountTeamMember is created in Salesforce.

    • Salesforce publishes an event for the new AccountTeamMember.

    • MuleSoft subscribes to this event, interprets it as an “add/activate” action, and calls Dataverse.

    • In the Dataverse API request, MuleSoft explicitly sets:

    • Status Reason = Active on the corresponding Internal Contact

  • Delete / Remove from Account Team

    • The AccountTeamMember row is deleted in Salesforce.

    • Salesforce publishes an event for the deleted AccountTeamMember.

    • MuleSoft subscribes to this event, interprets it as a “remove/deactivate” action, and calls Dataverse.

    • In the Dataverse API request, MuleSoft explicitly sets:

    • Status = Inactive and Status Reason = Inactive on the existing Internal Contact record

Dataverse ID Field Handling

For each integrated Salesforce object, Salesforce holds a Dataverse ID field (Dataverse_ID_c) which stores the unique identifier of the corresponding record in Dataverse. This field helps MuleSoft know if a record should be created or updated in Dataverse.

  • Dataverse IDs are system-generated by Dataverse, not Salesforce

New Salesforce record (Create event)

When Salesforce publishes a create platform event for a record:

  • There is no corresponding Dataverse record yet

  • The Dataverse_ID__c field must be blank (null)

Integration behaviour:

  1. MuleSoft receives the create platform event

  2. MuleSoft detects that Dataverse_ID__c is blank

  3. MuleSoft sends a create request to Dataverse

  4. Dataverse creates the record and generates a new Dataverse unique ID

  5. Dataverse returns the generated ID in the API response

  6. MuleSoft updates the originating Salesforce record and populates Dataverse_ID__c with the returned Dataverse ID

  7. Salesforce and Dataverse records are now linked 1:1

This ensures that all newly created Salesforce records are correctly created in Dataverse and subsequently treated as updates.

Existing Salesforce record (Update event)

  • When Salesforce publishes an update platform event for a record:

  • The record must already have a value in Dataverse_ID__c

Integration behaviour:

  1. MuleSoft receives the update platform event

  2. MuleSoft detects that Dataverse_ID__c is populated

  3. MuleSoft sends an update request to Dataverse using the Dataverse ID (or alternate key binding)

  4. Dataverse updates the existing record

Exception Handling and Data Integrity Rules

A Salesforce record must not be integrated to Dataverse under the following conditions:

Invalid ID scenarios

  • A create platform event is received and Dataverse_ID__c is populated (indicates incorrect pre-population or data corruption)

  • A migrated or previously integrated record does not have a value in Dataverse_ID__c

  • The value in Dataverse_ID__c:

    • is malformed

    • does not match the expected Dataverse ID format

    • does not correspond to an existing Dataverse record

Required behaviour (this needs to be reviewed and defined)

  • MuleSoft must not attempt a create or update in these scenarios

  • MuleSoft must raise a controlled integration exception that includes:

    • Salesforce object and record ID

    • Event type (create/update)

    • Dataverse_ID__c value (if present)

    • Reason for failure

Audit Fields

  • Dataverse system audit fields (createdon, modifiedon, created by etc) will remain under Dataverse control and will not be overwritten by values from Salesforce.

  • Salesforce audit fields (createddate, lastmodifieddate) will not be mapped into Dataverse, as no additional fields will be created in Dataverse to store them.

  • As a result:

    • Salesforce created Date represents when the record was first created in Salesforce

    • Dataverse createdon represents when the corresponding record was first created in Dataverse via Mulesoft.

  • Any reporting or analysis that requires the original Salesforce creation or modification timestamps must use data from Salesforce, not from Dataverse.

5.1 Creation of New Accounts

An Account becomes eligible to be sent from Salesforce to Dataverse when the following conditions are met:

  1. The Account is in the correct lifecycle status

    1. The account must have a Salesforce Status of Onboarding and Type = ‘Member’

    2. Or Status of Active for all other types

    3. These statuses indicate that the Account is operational and should exist in Dataverse.

In Salesforce:

  • A new account is created

  • This generates a new SalesforceID

  • The new PTY Code

  • PTY Code

  • Other attributies

  • Attempt an upsert using SalesforceID as an alternate key

  • If no row with this SalesforceID exists → create new Party row

  • New Dataverse GUID is auto-generated

Save:

  • PTY code from Salesforce

  • Other attributes

  • Dataverse returns its GUID → store in Salesforce Dataverse_Id_c

  • If not found → treat as an error

7. Dependencies & Assumptions

Contact Integration Timing and Dependencies

  • A Contact can only be integrated to Dataverse once its parent Account has been integrated and has a populated Dataverse_ID_c.

  • While an Account is in early lifecycle statuses (e.g., New, Prospect) and has not yet been sent to Dataverse, any related Contacts will not be integrated because the parent Party cannot be resolved.

  • Once the Account reaches Onboarding or Active and is successfully created in Dataverse, all eligible Contacts related to that Account can be integrated.

  • Contacts that reference an Account without a Dataverse_ID_c must not be integrated until this is populated.

IF Account.Dataverse_Id_c = Null. Do not send the contact

IF Account.Dataverse_Id_c = NOT NULL. Send the contact
