ADP single environment – Data flow and test-member solution

Corrected flow (VIPR sunset, ADP ingests bordereaux), the lower-env testing problem, and how the ADP test-member seed approach enables day-in day-out E2E testing.

1. Corrected data flow (current state)

VIPR is sunset. ADP is the system that ingests bordereaux files. To load those files, ADP needs Dynamics, CMT, and RDM data:

  • ADP holds a local copy of Dynamics RDM and CMT data inside ADP, used when loading files into ADP.
  • Once loaded in ADP, data is sent to ODS. ODS also refers to Dynamics RDM and CMT data, using its own version of that reference data (separate from ADP’s copy).

So there are two reference-data views: (1) ADP’s local copy for ingestion, (2) ODS’s (and downstream’s) copy for processing and validation.

2. The problem: ADP is single (broad) env only

ADP has only one environment (broad/prod). ODS, TDS, Dynamics, RDM, CMT have separate prod and non-prod / lower environments.

  • For E2E testing in lower envs, we need test data to flow through the pipeline into lower ODS → TDS → Dynamics F&O (and Tagetik/DCR where applicable).
  • Today, ADP runs in prod and uses prod Dynamics/RDM/CMT data for loads. So test data ingested via ADP is tied to prod reference data; getting that same data to lower ODS/TDS/Dynamics is the gap.

Because ADP is prod-only, test data must be ingestible in prod ADP and then flow to lower environments so we can run E2E tests there.

3. ADP solution: test members / test seed data in prod

The approach (aligned with ADP team and the seed-data architecture) is:

  • Define test members (and related test data) in the production environment so that ADP (prod) can ingest bordereaux for those members.
  • That ingested data is then routed or copied to lower ODS/TDS/Dynamics so E2E tests can run in lower env.

3.1 How test members are created (from ADP seed-data architecture)

From the it-test-member-portal seed-data architecture (e.g. 2026-02-03-seed-data-architecture.md):

  • Config: Test member configuration is defined in .ci/test_member_data.json (parties, repository files, optional AE reference and ae-fin-ops flags).
  • CI Flow Orchestrator (ci_flow.py): TestMemberCreation.run() runs a series of seed steps: seed_parties() → seed_repository_files() → seed_bdx_tracker() → seed_contracts(), seed_insurer_details(), seed_accounting_periods(), seed_member_controls() (AC-55911), seed_product_mappings().
  • Seeds are written to CSV files in submodules: ae-reference-data-dbt, data-domain-reference-data, and ae-fin-ops-dbt (e.g. written_member_control_prod.csv, claims_member_control_prod.csv).
  • A Git PR Helper creates PRs in those repos; once merged, seed data flows into Snowflake (RAW_BDX_ORCHESTRATOR) / ADP pipeline so test members exist in prod and can be used for loads.

So: test members (e.g. party_master_id TST-000001, repository files TS-9xxx) are created in prod via this seed pipeline; ADP then uses that data to ingest bordereaux for those members; the same pipeline can feed or sync to lower envs.

3.2 Sync challenge (RDM/CMT and member control)

Critical constraint: The RDM and CMT data (and member control) that ADP uses in prod for these test members must be in sync with the RDM/CMT (and member control) in the lower environment where we run Dynamics, ODS, and TDS. Otherwise:

  • Joins and validations in lower ODS/TDS/Dynamics may fail (e.g. party or member control not found, or wrong effective dates).
  • E2E assertions (e.g. Repository ID status, ledger lines) may not match.

So day-in day-out testing depends on:

  1. Test members and their seed data (including member control) being present and up to date in prod (ADP side).
  2. The same (or compatible) reference and member control data being present in lower Dynamics/ODS/TDS so that when data is ingested to lower env, it resolves correctly.

4. Limitations and assumptions

4.1 Regression-only: new contract types or new members

This approach only works for regression—i.e. when the contract type and member already exist in prod. If there is a new contract type or a new member that does not exist in prod:

  • ADP cannot clone or seed data for that test member, because there is no actual raw data in prod to clone from.
  • Tests that require brand-new contract types or brand-new members (e.g. for feature or UAT validation before prod release) are out of scope for this ADP test-member solution unless prod is updated first (e.g. new contract/member goes to prod, then clone/seed becomes possible).

So: the test-member solution covers “reuse existing prod data for E2E in lower”; it does not cover “test a contract/member that has never been in prod.”

4.2 Assumption: clone on demand by contract and member

A core assumption of the approach is that ADP will be able to clone (or seed) data on demand based on the contract and member that the test scenario refers to. In other words:

  • Tests are not limited to “whatever test members happen to be pre-seeded”; they need to target specific contracts and members.
  • The pipeline (or an API/process) should support something like: “for this test run, clone/seed data for contract X and member Y” so that the scenario has the right data in lower env.

If ADP cannot clone on demand by contract and member, test design is constrained to a fixed set of pre-seeded test members and contracts, which may not be enough for targeted scenarios.

4.3 Scale: many contract types and targeted contract testing

There could be on the order of 40 (or more) contract types, and the team may want to run tests for targeted contracts—e.g. “test only contract type A” or “test member M with contract type B.” The solution should support:

  • Cloning or seeding data for specific contract types and members that the scenario needs, rather than only a single generic test member.
  • Test scenarios (or test data config) that specify which contract(s) and member(s) are under test, so the right data is made available in lower env.

This ties back to the on-demand clone assumption: without it, covering 40 contract types with targeted tests would require pre-seeding and maintaining 40 (or more) test variants, which may not be practical.

Summary: The ADP test-member solution is regression-oriented and assumes on-demand clone/seed by contract and member. New contract types or new members not yet in prod are out of scope unless prod is updated first. For targeted testing across many contract types, confirm with the ADP team that clone-on-demand (or equivalent) is supported and how test scenarios can request specific contracts and members.

5. Day-in day-out E2E testing with this solution

A practical flow that uses the test-member approach:

  1. Ensure test members exist in prod: Run or rely on the ADP test-member creation flow (e.g. TestMemberCreation.run() and seed PRs) so that test parties (TST-######), repository files (TS-####), member control seeds, and related RDM/CMT-style data are present in prod and in the ADP pipeline.
  2. Keep lower env in sync: Ensure the lower environment (Dynamics, ODS, TDS) has the same—or a compatible—set of test members and reference/member control data (e.g. by deploying the same seed CSVs or equivalent to lower, or by a documented sync process). This addresses the “RDM/CMT in sync” requirement.
  3. Ingest test bordereaux in prod ADP: Use the test members (e.g. TS-#### files, test member IDs) to trigger or run a load in ADP (prod) so that test data is ingested.
  4. Route/copy to lower: Rely on the existing (or planned) mechanism that sends/copies that ingested data to lower ODS (and then TDS, Dynamics F&O, etc.).
  5. Run E2E tests in lower: Execute automation against lower ODS, TDS, and Dynamics F&O (and Tagetik/DCR if in scope), asserting on Repository ID, ledger lines, and other outcomes.

Ongoing work with the ADP team can focus on: (a) formalising the sync of RDM/CMT and member control between prod (ADP view) and lower (ODS/TDS/Dynamics view), and (b) any automation to re-seed or refresh test members when needed.
