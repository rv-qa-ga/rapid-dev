Lloyd's Pipeline – Automation-First Testing Plan

This document outlines how to test the Lloyd's flows (Tagetik, Dynamics F&O, ResQ, Non-Lloyds) with maximum automation and minimal full E2E, by testing at API level, integration points, and individual systems. It aligns with the existing framework and the QA Testing Strategy.

1. Principles

PrincipleMeaning
Automation firstPrefer automated API, data, and integration checks over manual or UI flows.
Avoid full E2E where possibleFull E2E (e.g. WBX file → … → Tagetik system) is slow and costly; use it only for a small set of critical paths or not at all in the first phase.
Test modules at API levelEach system (ADP, MuleSoft, TDS, ODS, Kafka, D365) is tested via its APIs or data interface.
Validate integration pointsTest one boundary at a time (e.g. ADP → MuleSoft, MuleSoft → TDS) with minimal data and clear assertions.
Reuse the frameworkUse existing MuleSoft steps, SQL Server/ODS steps, API clients, and tags; add Lloyd's-specific steps only when no reusable step exists.

2. Test Layers (Pyramid)

        ┌─────────────────┐
        │  Few / no      │  Full E2E (optional; only if business requires)
        │  full E2E      │  e.g. one "slice" per flow with minimal data
        ├─────────────────┤
        │  Integration   │  One boundary at a time: trigger or stub one side,
        │  point tests   │  assert on the other (e.g. MuleSoft → TDS row exists)
        ├─────────────────┤
        │  API / module  │  Many, fast: MuleSoft app status & logs, TDS/ODS
        │  & data tests  │  schema and data checks, regression (Lloyd's not in ODS/TDS)
        └─────────────────┘
  • Base (most tests): API and data checks – MuleSoft app status and logs, SQL assertions on TDS/ODS, regression queries. Fast, no end-to-end flow.
  • Middle: Integration-point tests – one boundary per scenario (e.g. "after MuleSoft run, TDS loader has expected row"). Optional short "slices" (e.g. trigger MuleSoft with test payload → assert TDS + ODS) without full user journey.
  • Top: Full E2E only if required; otherwise skip or keep to a single smoke path.

3.1 Tagetik flow (ADP → MuleSoft → TDS Tagetik loader → Tagetik system)

LayerWhat to testHow (framework)
ModuleMuleSoft app for Tagetik flow is running and logs are accessibleReuse MuleSoft-Log-Verification pattern: get application, get logs, search for flow name / correlation ID.
ModuleTDS Tagetik loader table exists and has expected columnsReuse SQL Server steps: run query against TDS DB (e.g. INFORMATION_SCHEMA.COLUMNS for loader table). Same pattern as ENG-145.

No full E2EDo not automate "WBX file → … → Tagetik system" in one scenario; break into the above.—

4. Leveraging the Framework

4.1 Existing assets to reuse

AssetUse for Lloyd's
MuleSoft steps (src/features/api/MuleSoft/, step-definitions)Get application status, get logs, search logs by flow/correlation ID, check for errors.
SQL Server steps (src/step-definitions/api/sqlserver/sqlserver.steps.ts)Run query in Reference / Intrali / Logging / Warehouse / TDS; execute stored procedure; run SSIS job step. Reuse for TDS loader checks, ODS Repository ID, regression.

Integration features (integration/mulesoft/, integration/sqlserver/)Pattern for "trigger one side, assert other side." Lloyd's integration tests follow same style.
Axios / API clientsHTTP calls to ADP, D365, or Kafka (if REST available).
Test data factoryBuild minimal payloads (e.g. test Repository ID, one WBX-like record) for repeatable tests.

4.2 Where to put Lloyd's tests

  • API / module / data: src/features/lloyds/ (e.g. tagetik-flow-api.feature, resq-flow-api.feature, dynamics-fo-flow-api.feature, regression-lloyds-exclusion.feature) or under api/ / integration/sqlserver/ with @lloyds tag.
  • Tags: @lloyds for all; @api for API-level; @integration for integration-point tests; @smoke for critical path; avoid @e2e unless necessary.

4.3 Run commands

# Lloyd's API and integration tests only (no UI, no full E2E)
npm run test:api -- --tags "@lloyds and (@api or @integration)"

# Smoke: MuleSoft + critical data/regression
npm run test:api -- --tags "@lloyds and @smoke"

# Regression only (Lloyd's exclusion + non-Lloyds path stable)
npm run test:api -- --tags "@lloyds and @regression"

# All Lloyd's (API + integration; exclude @e2e if you tag full E2E)
npm run test:api -- --tags "@lloyds"

5. Optional: Short "Slice" Tests (Minimal E2E)

If you need a small number of "almost E2E" scenarios without full UI or full journey:

  • Tagetik slice: Trigger MuleSoft with test payload → wait for completion (poll) → assert TDS Tagetik loader has row and (if applicable) Tagetik system received data.
  • ResQ slice: Same idea for ResQ flow: trigger → assert TDS ResQ loader.
  • Dynamics F&O slice: Trigger MuleSoft (e.g. journal flow) → wait → assert ODS Repository ID status and/or Kafka event.

Use test data factory for payloads and identifiers so slices stay stable and fast.

6. Summary

GoalApproach
Automate as much as possibleAPI + integration + data tests; reuse MuleSoft, SQL Server, and integration patterns.
Avoid costly full E2EDo not implement full WBX → … → Tagetik (or full Lloyds XML journey) as single E2E; split into module + integration-point tests.
Test modules at API levelMuleSoft (app + logs), TDS/ODS (SQL), ADP/D365/Kafka (APIs where available).
Validate integration pointsOne boundary at a time: ADP↔MuleSoft, MuleSoft↔TDS, MuleSoft↔Kafka, MuleSoft↔ODS, with clear assertions.
Leverage frameworkExisting MuleSoft steps, SQL Server steps, ENG-145-style features, tags, npm run test:api -- --tags @lloyds.

This gives you an automation-first strategy that maximizes coverage and speed while keeping cost and runtime under control.
