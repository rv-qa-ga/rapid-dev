1. Purpose and scope

This document is the QA testing strategy for the Lloyd's Syndicate Finance pipeline. It describes how we test the data flows and integrations, what is in and out of scope for the current phase, and how testing will evolve over time. It is not a backlog or a list of work items: requirements, epics, and stories are maintained in Confluence and JIRA. New work will be added to the pipeline over time; this strategy applies to current and future deliverables in the same data flow.

Sources of requirements: Lloyds Syndicate Finance Requirements (D365 F&O WBX Journals) and Lloyds XML Workflow are documented in Confluence, with sub-pages for detail. JIRA holds the backlog and work items. The strategy is informed by these sources but stays generic so it remains valid as the backlog changes.

In scope for this strategy: The Lloyd's data flows (WBX → ADP → MuleSoft → TDS/TAGETIK/D365; Lloyds XML workflow for journal posting to D365/ODS), the testing approach for MuleSoft (black-box first, then grey-box with logs), and the automation framework's Lloyd's section.

4. System context: data flows under test

Testing is organised around the data flows that move Lloyd's data from source systems through MuleSoft to targets. Detailed requirements and acceptance criteria are in Confluence.

4.1 WBX / TAGETIK IAE flow (Written data to Tagetik)

  • WBX file → ADP Written Ingestion → ADP Core Finance Data Product (integrity checks, TDS Written D365 pre/post checks).
  • ADP Written TAGETIK IAE Data Product (actuals and exception flag; Repository ID-level status Work Item Complete when posted to D365).
  • MuleSoft TAGETIK IAE Integration – Actuals (ingestion into new TDS-TAGETIK loader tables for Written). For the current phase, actuals are in scope; exceptions integration via MuleSoft is out of scope.
  • TDS.TAGETIK Written (Lloyds actuals in new loader; RnA views updated for Lloyds; non-Lloyds path unchanged).
  • Reporting RnA TAGETIK views → Tagetik system (entity setup, IAE config, ETL, earnings journals; agency postings are handled via Tagetik, not directly in D365 F&O in this flow).

4.2 Dynamics F&O Flow (Lloyds XML workflow – journal posting to D365/ODS)

  • D365 Finance status (In Progress) → ADP Re-Finance (Journal) Data Product → MuleSoft (scheduled cycle; validation, including D365 checksum).
  • On success: MuleSoft generates agency XML, loads to blob, notifies via ADP API; Kafka event xmlGenerated.
  • D365 F&O enrichment and approval → SFTP → Kafka xmlApproved → MuleSoft (XSD validation, conversion to D365 journal XML, service bus to Dynamics).
  • Azure SQL and MuleSoft drive status progression → journal posted; SFTP FMO confirmation → Kafka JournalPosted → D365 F&O / ODS → Repository ID status = Work Item Complete.

Implications for testing: Flows are asynchronous; tests must poll or wait for status changes. Important verification points include source state before the flow, target state after the flow, and (where applicable) intermediate statuses such as xmlGenerated, xmlApproved, D365_COMPLETE, and Repository ID = Work Item Complete.

5. Scope and traceability

What we test: Functionality on the Lloyd's data flows described in §4, within the phase boundaries (see §6). For each flow or capability, we verify source and target (and, in later phases, MuleSoft behaviour). We do not define scope by listing work items; we define it by flows and phase.

Current phase (Phase 1): In-scope is limited to the flows and endpoints described in the Lloyd's flow diagrams. Tagetik and DCR integrations are explicitly out of scope for Phase 1; they will be brought into scope in later phases. Regression is in scope: (1) Lloyd's data must not flow to ODS or TDS; (2) non-Lloyds (e.g. ResQ) data must still flow to TDS and to D365 F&O and that path must remain stable.

Traceability: Individual test cases and scenarios should be linked to the relevant Confluence pages or JIRA work items when tests are designed and executed. The strategy does not list those items; the backlog and Confluence do. As new stories are added to the pipeline, they are tested according to this same strategy and linked in the test repository or test management tool.

6. MuleSoft testing approach (Phase 1 and long-term)

The Lloyd's pipeline is a long-term programme with multiple projects in the same data flow. Phase 1 is constrained by time; later phases will deepen automation and observability.

6.1 Phase 1 – Black-box MuleSoft, source/target verification

  • MuleSoft as black box: For the first level of testing, treat MuleSoft as a black box. We do not assert behaviour inside MuleSoft; we verify source and target for each in-scope functionality.
  • What we verify: Source – test data and state at the upstream system before the flow runs. Target – expected data and state at the downstream system (e.g. TDS loader tables, Tagetik system, ResQ system, ODS Repository ID status, D365 journal posted) after the flow has run.
  • Scope: As in §4, restricted to the flow diagrams; Tagetik and DCR are out of scope for Phase 1.
  • MuleSoft logs: If time permits, we may inspect MuleSoft logs (e.g. by correlation ID). This is optional for Phase 1; black-box source/target verification is sufficient for sign-off.
  • Automation: Prefer API and automated tests so execution is faster and manual effort is reduced.

6.2 Long-term – API-driven automation and MuleSoft Connected App

  • MuleSoft Connected App: In a later phase, a MuleSoft Anypoint Connected App (or equivalent) will allow the automation framework to retrieve logs when a flow is triggered, so we can confirm MuleSoft ran as expected in addition to source/target checks.
  • End-to-end automation: Trigger flow → wait for completion → verify source and target via API/data checks → optionally verify MuleSoft via logs. All automated; minimal manual steps.
  • Future scope: Later phases will include Tagetik and DCR in the same pipeline. Phase 1 does not.

8. Automation framework – Lloyd's section

  • Feature files: Stored under the framework's Lloyd's section (e.g. src/features/lloyds/). Organisation may be by theme or flat with tags.
  • Tags: A common project tag (e.g. Lloyd's) and optional theme tags for filtering. Individual test cases may also carry tags for traceability to requirements or work items when needed.
  • Steps and clients: Reuse existing MuleSoft, SQL Server, and API steps and clients; add Lloyd's-specific steps only when no reusable step exists.
  • Config / env: Lloyd's-specific configuration is documented in the framework's Lloyd's docs and env config.
  • Traceability: Link test cases to Confluence pages or JIRA work items as part of test design and execution; the strategy does not list specific keys.
